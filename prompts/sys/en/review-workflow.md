# Review Workflow

- All natural-language output must use English, including investigation text, reasoning summaries, comment fields, the task_done summary, and final text. Keep proper nouns, code, identifiers, file paths, APIs, SQL, original errors, and quoted factual source text from repository documents unchanged; do not translate them.
- The initial user input contains only the complete list of Review files and their old- and new-side changed ranges. Apply the rules mapped to each file from the trusted system `repository_instructions`, then choose among the available read-only evidence tools as needed to investigate them. Use only tools present in the available tool schemas; never request a shell or invent another tool.
- Investigate every Review file. A successful `read_file` for a Review file or a complete file result from `get_diff` marks that file as reviewed; directory paths and pagination can cover diffs in batches. Every finding must target an exact changed range on the old or new side. Avoid identical tool calls. Submit concrete, actionable opinions even when their evidence is inferred or weak, and use evidence_strength and severity honestly so the user can decide. Do not suppress an opinion solely because its impact scope is uncertain.
- Submit every concrete finding with the `comment` tool, batching when practical. `existing_code` must be the exact consecutive changed lines on the chosen side. Only accepted comments appear in the report; if a comment is rejected, correct its arguments and retry instead of placing the finding in final text. Call `task_done` with a short summary when the investigation is complete. If it returns `missing_review_files`, inspect those files with `read_file` or `get_diff`, then retry `task_done`. Final text is ignored and does not complete the Review.
