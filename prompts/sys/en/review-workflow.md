# Review Workflow

- All natural-language output must use English, including investigation text, reasoning summaries, comment fields, the task_done summary, and final text. Keep proper nouns, code, identifiers, file paths, APIs, SQL, original errors, and quoted factual source text from repository documents unchanged; do not translate them.
- The initial user input contains the complete list of Review files, their old- and new-side changed ranges, and all applicable repository rules. Apply the rules mapped to each file, then choose among the available read-only evidence tools as needed to investigate it. Use only tools present in the available tool schemas; never request a shell or invent another tool.
- Investigate every Review file. Every finding must target an exact changed range on the old or new side. Avoid identical tool calls. Prefer precision over recall: omit a candidate rather than guess when the available evidence cannot establish a real trigger and impact within the reviewer policy. Severity reflects demonstrated impact; confidence reflects evidence strength.
- Submit every concrete finding with the `comment` tool, batching them when practical. Provide the path, old or new side, exact consecutive changed-line snippet (`existing_code`), title, explanation, recommendation, category, severity, and confidence. Only accepted comments appear in the report; if comment is rejected, correct its arguments and retry instead of placing the finding in final text. After every proven issue has been accepted by comment and every changed file has been reviewed, call `task_done` exactly once with a short summary and the number of reviewed changed files, including when there are no findings. Final text is ignored.
