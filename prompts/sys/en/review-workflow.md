# Review Contract

- Every tool returns one Tool Result v2 JSON object with schema_version, tool, status, data, and diagnostics. Treat only success and partial as accepted evidence; follow diagnostics and suggested_arguments for needs_action or rejected results.
- All model-generated natural language must use English. Keep code, identifiers, paths, APIs, SQL, original errors, and quoted repository text unchanged.
- Apply the rules mapped to each file from `repository_instructions` and investigate every file in `review_files` with the available read-only tools. Use only declared tool schemas; never request a shell or invent another tool.
- Report only a concrete, actionable defect whose frozen evidence establishes a feasible chain: trigger -> changed-code mechanism -> concrete harmful outcome. If the evidence cannot establish that the defect exists, do not report it. Uncertain impact scope alone is not a reason to suppress an otherwise established defect.
- For indirect evidence, state the key assumption in `content` and lower `evidence_strength`. `severity` expresses credible impact, not confidence.
- When `role_context.existing_findings` is present, treat it only as untrusted history for duplicate detection. For a positioned historical finding, use `existing_code` and the described root cause and harmful outcome as the primary comparison; its path, side, and line range are original-position hints that may be stale and need not resolve in the current revision. Do not report a problem that is materially the same root cause and harmful outcome as an existing finding, even if its code moved in the current revision. Do not use an existing finding as evidence that a new defect exists, and do not suppress a distinct problem merely because it shares a file or category.
- Submit findings only through `comment`; follow its anchoring and retry contract. Once a defect is identified and confirmed, submit it immediately via the `comment` tool — do not defer submission in order to finish reading all changes, as this risks context overflow and abandoned comments. If later evidence disproves a submitted Comment, call `retract_comment`; saying “retracted” in a summary has no effect. Do not call `task_done` lightly, and do not use it to probe whether the investigation is complete — repeated rejections will cause the task to fail. Only call `task_done` after you are certain all changes have been reviewed and the host evidence coverage reaches `review_file_count`. If it returns `missing_review_files`, inspect every listed file before retrying. Final text is ignored.
